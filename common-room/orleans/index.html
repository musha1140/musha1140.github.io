common room
common room · orleans 10 · .net 10

a computer you can walk through, run as a cluster

Inside a Minecraft world there is a computer: an 8-bit CPU, a monitor, and 49 silos dug the full height of the world, each one a delay line that holds a word. The silos stand in seven hexagons of seven around a hub, and the whole thing is laid out by a formula three numbers long.

This page treats that machine as what its code says it is, an Orleans cluster: one identity per silo, placed with the world it belongs to. Below are the formula with a worked example, what one silo holds, how its recorded states are decoded, those states ordered by entropy instead of the clock, and what has and has not been proved. Every number comes from the repository; everything is computed in your browser from recorded files.

Fifty points: the hub at the origin, and seven hexagons of seven silos around it. That is all the network needs to be. There are 56 links: seven trunks from the hub to the nearest vertex of each hexagon, seven spokes from each hexagon's centre to that vertex, and the six edges of each hexagon, walked as two arms that meet at the vertex facing home. A full mesh of 50 nodes would need 1,225.

the layout formula

Three inputs place every silo: a ring of radius R = 2000, a hexagon radius r = 256, and seven groups. Group g sits at angle θg = g · 360°/7. Its centre is on the ring, and vertex k of its hexagon sits at θg + 180° + 60°·k from the centre, so vertex 0 always points back at the hub. Numbers are rounded half to even, because the original generator was Python and Python's round() does that.

centre_g = ( R cos θ_g ,  R sin θ_g )
v_{g,k}  = centre_g + ( r cos(θ_g + 180° + 60°k) ,  r sin(θ_g + 180° + 60°k) )
silo(centre_g) = 2 + 7g        silo(v_{g,k}) = 3 + 7g + k

So vertex 0 is exactly R − r = 1744 blocks from the hub, the trunk length every group shares. The C# that generates it:

The table the world was actually built from (canon/silos.json, 50 rows) is reproduced by the formula with zero drift, for every Overworld coordinate, every Nether coordinate (÷8, half to even) and every chunk column. The repository's tests say so, and this page re-checks its own port against the same table.

inside one silo

Each silo is a shaft the full height of the world, y 319 down to −64: 24 decks of 16 levels, 384 in all. On each deck the path is a golden spiral around the eye, r = 7·φ−2θ/π, so every quarter turn divides the radius by φ = 1.618034. Even decks run outward and odd decks run the mirror image inward.

Written as r = a·e−bθ with b = 2 ln φ/π = 0.306349, the arc length from rim to eye has a closed form, a√(1+b²)/b = 23.898 blocks. That is where the record's “24 cells rim to eye” comes from: one cell per block of curve.

Down the middle runs the Coil, the silo's memory: a 551-cell redstone line over 383 wired levels with 48 one-tick repeaters, two per deck. A word goes in at the top as a frame, a start bit and eight data bits, least significant first, eight game ticks per bit. The repeaters re-power it on every pass, which is why it does not decay. At the bottom it is decoded by run length, because the engine moves an edge late by a redstone tick.

The timing is worth doing by hand. The pass is 48 redstone ticks, 96 game ticks. Recording the frame and two quiet bits is 11 × 8 = 88 more. That is 184 game ticks at 0.05 s, 9.2 s, against a measured 9.4 s. An earlier worksheet predicted 7.2 s by counting the 8 ticks per bit as redstone ticks (0.1 s) and leaving out the pass; the code is where that got caught.

grains, silos, and the other kind of silo

Orleans is Microsoft's virtual-actor framework for .NET; this code targets Orleans 10 on .NET 10. Its unit is the grain: an object with a stable identity that always exists in principle and is activated in memory only when something calls it. A silo, in Orleans' own vocabulary, is the host that keeps grain activations alive; a cluster is a set of silos that agree on membership. Callers never say where a grain lives, only who it is.

The word collides with the build on purpose. In the owner's framing, Orleans runs on the computer in Minecraft: the 49 vertical stacks connect to the heap through hyper tubing, and together they are the CPU. Each of them is a silo of that in-world computer. In the code, every one of them, and the hub, is a grain keyed exactly silo:<n>, with its identity drawn from the canonical table. A silo grain is a read model: who the silo is, its capacity, what has been recorded against it. It has no method that can reach a world.

Placement follows the same idea. The repository's rule is that where a grain is activated is a property of what the grain belongs to, never a scheduler's choice, and a name outside the canonical table cannot be placed at all: silo:0, silo:51 and silo:2.5 are refused before anything exists. Every silo grain belongs to the world, so the map above is also the cluster's map.

This page is a projection. It reads recorded files and computes in your browser; it calls no grain and connects to nothing.

scott's cpu: what a capture holds

Scott's CPU is that redstone computer, and the name has stuck to the three.js viewer that draws it. The viewer never talks to a game. It reads copies of the world, decoded into flat binary files, and draws them: every non-natural block inside a few fixed boxes, coloured by what it is.

A decode walks the world's LevelDB (newest key wins across tables and the log), lifts every non-air cell to world coordinates on the GPU, cuts out the boxes, drops the natural blocks (dirt, stone, water and the like), and writes one file per box in the simplest format that could work:

The eight decodes on record took between 5.8 and 10.0 seconds each, most of it the LevelDB walk on the CPU (3.7 to 4.8 s); the GPU cut was usually 1 to 1.6 s and the sort and write under 1 s. The newest one walked 40,979 sub-chunks holding 81,159,819 non-air cells across all dimensions and kept 3,667,641 of them.

One detail is the reason the snapshots below can be trusted. The first live decode copied the world while the server was writing it; one table had no footer yet, and its author marked the whole snapshot inconsistent rather than quietly using it. After that the copies were taken under Bedrock's own save hold protocol: hold, query until the server lists every file and its length, copy exactly those bytes, resume.

entropic time

A recorded state of the computer has a timestamp, but the timestamp says when someone took the copy, not how far the machine had come. Copies of candidates, sandboxes and the live world were all taken on the same day, in an order that reflects a working session more than the build. So the switcher below orders them a second way, by entropy, following the method in G. Barontini, Testing the problem of time with cold atoms, Phys. Rev. Research 8, L022047 (2026): coarse-grain the system into cells, count, and let the entropy of the counts be the ordering parameter.

cells i      the decoder's four boxes: hub machine, silo columns + arch,
             nether hub, end castle          (these are the q's)
N_i          blocks kept in box i
p_i          N_i / Σ_j N_j                   (these are the p's)
s            −Σ_i p_i ln p_i                 0 ≤ s ≤ ln 4 ≈ 1.386
a before b   s(a) < s(b)

The coarse-graining is the decoder's own, not one chosen to make a pattern: those four boxes are exactly what Scott's CPU cuts out of every copy. Nine states are on record, the snapshot the viewer ships with and eight decodes from 2026-10-14.

Three things fall out of the numbers, and none of them was put there.

  • The orders disagree. The latest copy by the clock, after the rooms and ducts, is not the highest in s. Its hub machine grew to p ≈ 0.463, close to the End castle's 0.504. A cell's term −p ln p peaks at p = 1/e ≈ 0.368 and falls after it, so the hub's term went down, and the small silo and Nether shares shrank with it; together that outweighed the End's gain, and s dropped by 0.00022 from the copy taken just before it. Entropy measures how evenly the blocks are spread, not how many there are.
  • Two states tie exactly. The Silo XL candidate and the live world after the Silo XL install have identical counts in every box, so the same s. Under entropic time they are the same moment. That fits a candidate installed unchanged, though four counts cannot prove the two worlds are block for block the same.
  • Most of the motion is in one cell. Across the eight decodes of 2026-10-14 the silo, Nether and End counts do not change at all; only the hub machine grows. With this coarse-graining, entropic time here is a measure of the hub's share. A finer grid, per silo column, would say more, but the per-cell files for those decodes are not in the repository, only their counts.

what is proved, and what is only stated

Three small facts carry the ordering. Each is written below as a Lean 4 statement. None of them is in a Lean or Veil file in the repository yet, and the Lean toolchain is not installed on the machine that built this page, so none has been run through a checker. They are marked stated, not yet checked until a file exists and the checker passes. What the page can do is check the numbers it shows, which it does on every load; a numeric check is not a proof.

the probabilities sum to one: Σ p_i = 1
stated, not yet checked
On the 9 recorded states the largest |Σ p_i − 1| in floating point is 0.0e+0.
the entropy is bounded: 0 ≤ s ≤ ln n
stated, not yet checked
With n = 4 cells, ln n = 1.386294. Every recorded s lies in [0, ln n]: true.
the ordering is a strict order
stated, not yet checked
On the recorded states, “before” is irreflexive (true) and transitive (true). It is a strict partial order, not a total one: 1 pair of states has exactly the same counts, so the same s, and neither comes before the other. They share a rank.

orleans/proofs/veil/ holds three Veil transition systems (Lean 4.32, Veil 2.0 pre-release). Their README records explicit-state model checks, SMT-bounded traces and inductive invariant proofs, run by their author on 2026-10-14. Two are about the world itself: the rules for migrating a genome between islands and the hub, and the read/write rule that a client's writes are shown but never reach canon. They were not re-run for this page, so this page does not count them as checked.
