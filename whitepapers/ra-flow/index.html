Whitepaper

A Deterministic Flow & Proof Engine

Flow described in full, the service deliberately deferred

A small engine that turns a body of verbatim normative text into a deterministic workflow: structured intake, derived obligations, an ordered signing flow, and proof runs that re-execute the whole pipeline and diff the artifacts. This paper describes the flow and the proof discipline only. It names no use case on purpose: the engine stays an engine until it can exist in entirety, and that is scheduled for the last phase.

Text as the source of truth

The engine's rules are not paraphrased into code; the governing text is carried verbatim in the repository and the workflow's steps are written against it, section by section. When the text and the code disagree, the text wins by construction, the code cites its section the way a filing cites its statute. Which body of text, and for which purpose, is exactly what this paper declines to say.

The flow

Intake is structured and validated; from a validated intake the engine derives the obligations that apply, orders them, and walks a signing flow in which each step's output is the next step's input, deterministically, with no hidden state and no external dependency. The implementation is dependency-free on a current runtime, and every step is unit-tested through the platform's own test runner: the engine is small enough to be read and boring enough to be trusted.

Proof runs

The distinguishing habit is the proof runner: the entire pipeline is executed against fixture inputs, its artifacts written out, then executed again and diffed. A clean re-run is the reproducibility claim made mechanical, the engine does not merely say it is deterministic, it emits the evidence on demand, twice, and shows the delta is empty.

What this is not, yet

This is not a service, and this paper claims no use case for it. An engine that would carry real duties for real parties is only allowed to become a service when it can exist in entirety, code, custody and duty together, with the operational half as real as the software half. That threshold is scheduled deliberately: in the last phase, behind the always-on GSL node and its private tunnel (see the MDTGF paper), where an engine that must always answer can actually always answer. Until then it remains what it is here, a flow, described in full, with its proofs attached.

Deliberate omissions, this paper describes structure and mechanism, not implementation absolutes. Exact constants, derivation orders, offsets, thresholds, schedules and parameter choices are omitted by design: enough to see the shape and the work, never enough to reconstruct the keys. The repositories and live artifacts remain the reference implementations.
